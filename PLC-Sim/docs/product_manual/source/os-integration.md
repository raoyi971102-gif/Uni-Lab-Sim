# 与 Uni-Lab OS 联调

:::{admonition} 阅读角色
- **业务负责人**：确认设备用途、动作名称、参数单位、成功标准和安全边界。
- **开发人员**：把仿真 Endpoint 写进启动图，并完成三层就绪检查。
- **验收人员**：验证越界、断线、超时、联锁、未知结果，以及之后如何切到真机。
:::

PLC-Sim 只在用户设备包明确声明需要 PLC 或 OPC UA 通信时使用。它用于在没有真实产线的情况下验证连接、点位映射、握手顺序、超时和故障处理，不能代替真机安全验收。

本页对应 Uni-Lab OS 产品手册中的「PLC / OPC UA 仿真器」要求，从仿真器一侧说明如何满足那些交付项。

`unilab workspace init` 只生成无硬件副作用的最小设备包骨架，不包含物料类型、PLC 协议适配、PLC-Sim 配置或生产启动图。要用本仿真器联调，必须另外准备点表、模拟 Endpoint、握手规则和专用启动图。

## 启动顺序

1. 选择设备包提供的模拟配置，确认没有生产 PLC 地址。
2. 启动 OPC UA Server，检查监听地址和命名空间。
3. 如果设备包需要握手代理，等待 Server 就绪后再启动代理。
4. 启动 Uni-Lab OS，使启动图中的 PLC 节点建立会话。
5. 打开 Uni-Lab OS 页面，执行只读检查或安全测试动作。

顺序可以由设备包的启动脚本自动完成，但脚本仍应输出每个组件的状态。不要仅凭仿真器网页或 OS 网页能打开就判断协议链路正常。

PLC-Sim 联调必须让 Driver 真正连接 OPC UA。Uni-Lab OS 应使用 `normal`，并用专用启动图把端点限制在本机仿真器。`dry-run` 只生成模拟动作回执，不构造驱动，不能用来验证本页的协议链路。不要仅凭“使用了 PLC-Sim”就把任意 `normal` 启动图视为安全。

## 启动图配置规则

```json
{
  "id": "plc_gateway_01",
  "class": "community.example_lab.plc_gateway",
  "config": {
    "endpoint": "opc.tcp://127.0.0.1:4855/xuse_sim/",
    "namespace_uri": "urn:xuse:sim",
    "connect_timeout_seconds": 10,
    "command_timeout_seconds": 60
  }
}
```

示例值仅用于解释字段。实际字段名和设备类从用户设备包检查报告取得，并遵守以下规则：

- HTTP 管理页面地址不能填入 OPC UA `endpoint`；
- 测试启动图与生产启动图分开保存，生产地址不得出现在模拟配置中；
- 优先使用 Namespace URI；只能使用 Index 时，必须确认服务重启后编号不会变化；
- 点位名称、数据类型和读写方向必须与点表一致；
- 连接超时与动作超时分开设置，单位写清楚；
- 账号、私钥和证书密码通过受控配置注入，不写入启动图。

## 启动图与仿真器对照表

设备包应提供一张对照表，说明每个设备实例连接哪个端点、使用哪组点位：

| 启动图实例 | 仿真 Endpoint | 点表 | 握手代理 | 备注 |
| --- | --- | --- | --- | --- |
| 例如 `plc_gateway_01` | `opc.tcp://127.0.0.1:4855/xuse_sim/` | `szlab_plc_0810.csv` | SZLab 设备包模式 | 本机回环 |
| 例如 PTLC 工位网关 | 同一 Endpoint，`profile=ptlc` | `config/ptlc_nodes.yaml` | PTLC L2 | 与 CSV profile 不要混用 |

表中的实例名必须替换为设备包实际 ID。

## 三层就绪检查

| 层级 | 要看什么 | 通过标准 |
| --- | --- | --- |
| 进程层 | 仿真器和可选握手代理 | 进程运行，日志没有持续重启 |
| 协议层 | OPC UA Server | Endpoint 可连接，命名空间和关键点位存在 |
| 系统层 | Uni-Lab OS | PLC 设备在线，订阅和写入没有类型错误 |

若仿真器提供 Web 页面，页面只用于观察和受控测试。共享环境中不要修改点位、切换场景或停止服务。

## 最小联调步骤

1. 读取一个只读状态点，核对类型和值。
2. 在无硬件副作用的前提下写入测试命令。
3. 观察“命令已接收 → 执行中 → 完成”的状态变化。
4. 复位命令并确认状态返回空闲。
5. 分别模拟拒绝、超时和故障，确认工作流明确失败且不会自动重复危险动作。
6. 重启仿真器，确认 Uni-Lab OS 能按设备包规定的策略恢复连接。

SZLab 场景下，OS 工作流调用的是设备动作名，不是 NodeId。驱动把动作翻译成点位握手；仿真器只保证点位按协议变化。物料位置和库存仍以 OS 为准。

PTLC 联合仿真应使用 `federated` 传感器模式。PLC-Sim 不推断机器人是否已经取走瓶子；外部模拟器通过 `world-file` 或 GUI 的物料事件提交幂等现场事实。

## 切换到真实 PLC

切换前复制并锁定一份生产启动图，由现场负责人填写真实 Endpoint、证书和点位配置。先完成只读连接，再进行单动作低风险测试，最后才执行完整工作流。

仿真器中通过的结果只证明软件合同基本一致。急停、互锁、限位、人员防护和异常恢复仍必须由现场安全验收确认。

## 自动化验收包

仓库内的 `plc-acceptance-kit` 用于按证据等级跑门禁，不是 PLC-Sim 本体。L1 通过不自动升级为软 PLC 或真机验收。使用说明见 `plc-acceptance-kit/使用说明.md`。

## 常见问题

| 现象 | 检查重点 |
| --- | --- |
| OS 页面可用但设备离线 | Server 是否启动、启动图是否使用协议地址、OS 是否已建立设备连接 |
| BadNodeIdUnknown | 点位名称或命名空间不一致 |
| 写入类型错误 | 启动图参数类型与点表数据类型不一致 |
| 动作一直运行 | 完成/复位点没有按握手规则变化，或动作超时配置过长 |
| 任务重复产生动作 | 超时后未经现场确认就重新提交；先查询原命令状态 |

完成仿真联调后，按 Uni-Lab OS 手册保存设备包版本、启动图和测试结果。
